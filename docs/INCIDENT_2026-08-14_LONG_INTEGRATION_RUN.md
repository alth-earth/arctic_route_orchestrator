## 4. 为什么慢

这条测试完全使用本地夹具、`LocalArchiveSource` 和本地包，不发 HTTP 请求。代理环境变量虽然
存在，但不是本次瓶颈。

主要成本在 C：

- A* 状态包含 `(node, hourly time bucket, heading)`；即使 `11×26` 网格也约有
  `11×26×169×9 = 435,006` 个理论状态；
- 单次搜索最多展开 250,000 个状态；每状态最多检查 8 条边；
- 每条边有两轮速度修正，每轮至少三个风险采样点；
- `RiskSampler` 每次时间 bracket 当前线性扫描最多 169 帧，并重复取得 xarray 数组；
- v2 初始/重规划各跑三目标，共 6 次搜索；v3 初始/重规划理论上再跑 24 次；
- 每次规划准备还会对完整 RiskFrame 窗口做 canonical 私有快照。

因此，把 v2 与 v3 初始/重规划参数放进同一集成用例，理论上会串行触发 30 次搜索。节点减少
能降低制品和搜索空间，但没有解决时间索引、重复采样与多目标串行的根因。

## 7. 后续运行手册

### 7.1 启动前

1. 明确宣布将运行的阶段、网格、目标数、预计搜索次数、超时和输出目录。
2. 检查是否已有同 run 的 pytest/orchestrator/下载任务，避免重复启动。
3. 先运行小窗、单目标、低节点 smoke；只有它通过才升级到完整 v2，再单独运行 v3。
4. v2 与 v3 分命令/分报告，不在一个 pytest 参数化用例中串行完整初始和重规划。
5. 复用已通过哈希校验的 A fixture/B committed window，避免每次重建 1412 个归档文件。

### 7.2 运行中

每阶段至少持久化并输出一次开始/结束/心跳：

- A 发布与 exact resolver；
- B build、full commit、suffix commit；
- C 每个目标的初始规划和重规划；
- v3 每一层/目标；
- 当前展开数、open-set 峰值、风险采样次数、耗时和 RSS。

为每阶段和每个目标设置明确超时。超时保存当前目标、展开量和已有制品，然后明确失败；不能让
UI 只显示“仍在执行”而没有可判断的进度。

### 7.3 优化顺序

1. 为 `RiskSampler` 建立时间二分索引，并缓存帧数组/坐标视图；
2. 避免同 committed window 的重复 canonical 快照；
3. 为三个目标复用可安全共享的预处理结果；
4. 记录并评估搜索上限和早停；
5. 再比较 `0.5°×1.5°` 与 `0.75°×2.2°` 的路线、耗时和风险保真。

这些优化涉及 C 核心时，应单独审批并保证算法语义/合同不因性能修复被静默改变。
